# LabAgents MVP design

## Product Capabilities

用户以自然语言提出研究目标，系统能够把它收敛为可执行的 procedure，并协助完成实验规划、参数整理、运行组织与结果回流。
LabAgents 当前阶段的目标不把安全、审批、审计一次性做完整，而是先把 agent 的实验规划与实验操作能力搭起来，并让真实实验操作过程尽量顺畅可用。

当前版本优先具备以下特征：

1. **目标可表达**  
   用户可以用自然语言描述实验目的、假设与约束，系统能够将其整理为结构化研究意图。

2. **规划可落地**  
   用户目标能够被整理、补全并转成 agent 可以持续使用的实验规划与执行输入，而不是停留在聊天层。

3. **操作可顺畅**  
   系统应优先支持实验操作本身顺畅进行，包括参数准备、运行发起、过程观察和必要的人工介入。

4. **能力可理解**  
   系统对上暴露的是语义化实验能力，而不是零散底层驱动命令，便于 agent 规划、人类审查与安全验证。

5. **运行可托管**  
   长周期实验仍应由 kernel 托管，具备基本的异步观测、暂停/中止、恢复与状态追踪能力。

6. **安全与审计最小化设计**  
   当前版本允许安全机制、审批机制和审计能力不完整，重点是先验证 agent 是否真正具备实验规划与操作能力；更严格的安全闭环留给后续版本。

## Core Ideas

1. **先把实验规划和实验操作跑通。**
当前阶段优先验证 agent 是否能把研究目标整理成可执行步骤，并协助完成参数准备、运行发起、过程观察和结果回流。安全、审批、审计先不追求完整闭环。

2. **LLM 负责规划与组织，不进入执行热路径。**
agent 主要负责理解目标、整理参数、生成执行输入、解释结果和提出下一步建议。真正的运行过程应尽量由确定性执行层接管，避免边跑边让模型临场决策。

3. **执行输入需要结构化，但不过早追求过重抽象。**
自然语言目标最终要落成可执行的结构化输入，便于复用、检查和运行。但这一阶段重点是让结构化输入真正服务实验操作，而不是先把数据模型设计得过满。

4. **系统对上暴露语义化实验能力，而不是底层驱动命令。**
agent 理解的是“采谱、对焦、移动到点位、做 mapping”这类实验能力，而不是串口命令、文件桥细节或仪器协议细节。底层细节留在 runtime / driver 层。

5. **运行过程要可观察、可暂停、可恢复。**
只要进入真实实验操作，系统就应尽量具备基本托管能力：知道 run 在哪、做到了哪、能否暂停、中止后怎样恢复。这里先追求够用，不追求一次性做成完整运行平台。

6. **安全先围绕最小危险场景收敛。**
当前只优先关心两类明确危险：样品撞镜头、激光功率过高伤样品。其他更复杂的审批、风险分级和审计闭环放到后续版本。

## Core Data Boundaries

为了约束用户和 agent 在实验流程中的交互数据，当前推荐把核心对象分成三层，并尽量让每层各自承担清楚的职责：

1. **`ExperimentIntent`**
   面向 planner / analyst / lineage，表达研究目标、假设、为什么做这一轮。
   它属于研究层，不进入 kernel。

2. **`ProcedureSpec`**
   面向 kernel，表达“执行哪个 procedure、参数是什么、资源是什么、停止条件是什么”。
   它是 kernel 的唯一执行输入。当前阶段两类最小危险（样品撞镜头、激光功率过高）
   直接以约束字段（`limits`）随 spec 携带，不单独抽一层 policy 对象。

3. **`RunState`**
   面向 runtime / records / watcher / resume，表达进度、heartbeat、unit 状态、
   pause/abort、artifacts。它属于运行时真相，不属于 spec。

当前建议保持以下边界习惯：

- `ExperimentIntent` 可以影响 `ProcedureSpec`，但不能直接执行。
- `ProcedureSpec` 不自行携带审批结论；人工确认（启动前批准、危险动作的即时确认）作为运行编排层的 gate 处理，不进入 spec 本体。
- `RunState` 只能由 runtime 产生，不能由 planner 预写。
- kernel 只消费 `ProcedureSpec`，不直接消费 `ExperimentIntent`。

> 注：更完整的运行准入 / 监督 / lease 契约（即 `RunPolicy`）属于 Safety 章节描述的目标态，
> 当前版本不实例化为独立核心对象，最小危险先由 `ProcedureSpec.limits` + 启动前人工确认承载。
>
> 注：硬件能力与实验环境状态（见 Context management）由 runtime 作为上下文提供，
> 不建模为这一层的交互对象；它们影响规划与准入校验，但不由 planner 写入。

更具体的数据模型、字段归属与关系定义见 `data_model.md`。

## Context management

当前阶段，实验 Agent 的 context 不需要追求复杂体系化管理，重点是把实验规划和实验操作真正依赖的上下文保留下来。与普通 Agent 相比，至少有三类信息不能丢：

1. **硬件能力信息** — agent 至少要知道当前有哪些仪器、能做哪些实验动作、哪些动作是假的、哪些动作能连到真实设备。

2. **当前实验环境信息** — agent 需要知道实验室当前资源和设备状态，否则规划出来的步骤很容易不可执行。

3. **运行与结果信息** — 已经做过什么、当前 run 到哪里、产物放在哪，这些信息不能只靠对话记忆，至少要有结构化记录可回看。


## Instrument Integration

当前阶段，仪器接入的重点不是先把完整执行架构定义得很漂亮，而是让 agent 能基于稳定接口完成实验规划和实验操作。它不应只是“把协议包装成一组 tool”，但也不必一开始就展开成过重的体系。

### 接入与调用要点

1. **优先暴露语义化实验动作**：GPIB/USB/VISA 等底层协议不直接暴露给 agent。当前更重要的是让 agent 面向“采谱、对焦、移动、mapping”这类实验动作，而不是直接拼底层命令。

2. **执行入口尽量统一**：真实运行最好还是通过结构化执行输入进入执行层，避免不同仪器各自暴露一套临时调用方式，后面难以维护。

3. **先把状态回传做实用**：比起复杂建模，当前更重要的是每次操作后能拿到足够有用的结果，例如是否成功、当前位置、耗时、生成了哪些产物。

4. **长时操作不要卡死在前台**：扫描、等待稳定、长时间采集这类操作需要有基本的异步观测能力，避免 planner turn 被长时间阻塞。

5. **错误先做到可判断、可恢复**：当前不必先做完整错误体系，但至少要区分“能否重试”“是否需要人工介入”“是否应该停止当前 run”。

6. **保留 fake / mock 路径**：没有硬件时仍然要能调试 agent 的规划和操作链路，否则开发成本会过高。

**当前阶段的核心原则**：仪器接入首先服务于 agent 的实验规划与实验操作能力验证。只要能稳定暴露语义能力、统一执行入口、返回足够有用的状态，并保留无硬件调试路径，这一阶段就算达到目标。

## Safety

本节描述的是 Raman MVP 希望逐步收敛到的安全目标态，不代表当前版本已经把这些机制完整实现。当前阶段仍以验证 agent 的实验规划与实验操作能力为主，安全机制会先围绕最小危险场景逐步补齐。

目标态上，Raman 将优先收敛到一种安全模型：**有人监督的 `live-supervised` 运行**。
系统目标不是让 agent 自主控制实验，而是把 agent 约束为受监督的执行助手。后续版本的最小 safety 设计优先防三类最现实的错误：

1. 在实验室或设备未 ready 时启动 run
2. 运动越过安全边界，导致样品撞镜头
3. 激光功率过高，导致样品受损

其中第 1 类属于**准入问题**，由启动前检查（admission）拦截；第 2、3 类才是需要 hazard 约束硬限制的「两类明确危险」，与前文 Core Ideas / Core Data Boundaries 所说的两类一致。

### 目标态三层安全体系

1. **确定性内核** — 所有硬件指令由 kernel 发出，LLM 不直连硬件。
2. **规则看门狗** — 非 LLM 的规则引擎实时监控运行状态，仅具备暂停/中止权限。
3. **监督操作者** — 人负责批准 run 启动、对明确危险场景做确认，并在需要时暂停/中止。

目标态上，安全验证也分层放置：主要针对 semantic capability、`ProcedureSpec` 和 `RunPolicy` 做高层与准入校验；runtime / driver 负责最终硬防线。工具接口不是唯一安全边界，更不是全部安全语义的承载层。

### Target Safety Rules

当前版本不做复杂审批流，也不做 agent-autonomous mode。后续收敛时，`RunPolicy` 会优先承载以下最小约束：

1. **固定 mode gate** — 仅允许 `live-supervised`。
2. **最小 admission** — run 启动前必须同时满足：监督人在场、执行前检查已通过、当前设备控制权可用。
3. **危险约束收窄到两项** — 不对所有 effectful step 做逐步确认；当前只关心两类明确危险：样品撞镜头，以及激光功率过高导致样品受损。
4. **高功率激光需人工确认** — 只有当激光功率超过用户提供的安全阈值时，才要求用户确认后才能下发。
5. **设备控制 lease** — live run 启动后获取独占控制权；lease 释放前不允许新的 live run 抢占。
6. **人工可随时接管** — 监督人可以 pause / abort，watchdog 也可在异常时中止。

### `RunPolicy` 的目标最小语义

在 supervised MVP 的目标态里，`RunPolicy` 不是通用 policy engine，而是一次 run 的最小安全契约。它至少需要表达：

- 当前 run 是否绑定 `live-supervised`
- 是否要求监督人在场
- 启动前是否已经通过执行前检查并持有当前设备控制权
- 哪些明确危险需要额外确认或硬限制
- 需要持有哪些设备控制 lease

更复杂的风险分级、多角色审批、跨 run 安全白名单先不进入这一版。
